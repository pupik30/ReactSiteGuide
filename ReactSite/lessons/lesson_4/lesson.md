В [уроке 3](../lesson_3/lesson.md) вы собрали собственный образ из `Dockerfile` и запустили контейнер. В этом уроке разберём особенности сборки образов с внешними библиотеками, образ из контейнера и очистку кэша.

Цель урока — добавить внешнюю библиотеку в образ, разобраться в повторной сборке и сохранить изменения контейнера.

Перед началом запустите Docker Desktop (на Linux — Docker Engine) и проверьте:

```bash
docker version
```

В выводе должны быть блоки `Client` и `Server`. Все примеры рассчитаны на Linux-контейнеры.

## Внешние библиотеки в образе

В прошлом уроке программа использовала только интерпретатор. Если в коде есть `import` сторонней библиотеки, её нужно установить **в образ**. Установка на вашем компьютере не делает библиотеку доступной контейнеру.

Откройте в редакторе папку `lessons/lesson_4` и создайте три файла. Это самостоятельный учебный пример по теме ролика.

Файл `main.py`:

```python
import requests

print("Библиотека requests доступна, версия:", requests.__version__)
```

Файл `requirements.txt` — список зависимостей:

```text
requests==2.32.3
```

Здесь зафиксирована версия прямой зависимости для повторения примера. Полная фиксация среды также потребовала бы фиксировать её зависимости и базовый образ по digest.

Файл `Dockerfile`:

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY main.py .
CMD ["python", "main.py"]
```

`RUN` выполняется при сборке, `CMD` — при запуске контейнера. Флаг `--no-cache-dir` относится к кэшу pip, а не к кэшу сборки Docker.

Откройте терминал в этой папке:

```bash
docker build -t lesson4-python:1 .
docker run --rm lesson4-python:1
```

При первой сборке нужен интернет для загрузки базового образа и пакетов. При запуске программа только выводит версию установленной библиотеки; сетевой запрос не выполняется.

## Образ из контейнера

После создания контейнера изменения его файлов попадают в отдельный записываемый слой. Исходный образ при этом не меняется. Посмотрим это на небольшом примере:

```bash
docker run --name lesson4-edit python:3.12-slim sh -c "echo changed > /tmp/note.txt"
docker diff lesson4-edit
docker commit lesson4-edit lesson4-snapshot:1
docker run --rm lesson4-snapshot:1 cat /tmp/note.txt
```

Последняя команда должна вывести `changed`. Первая команда создала файл, после чего контейнер завершился. `docker commit` сохранил его файловые изменения в новый образ. Команда после имени образа (`cat /tmp/note.txt`) заменяет команду запуска по умолчанию.

Данные подключённых томов в `commit` не входят. Для учебного эксперимента снимок удобен, но рабочий проект лучше описывать через Dockerfile: коллега должен видеть, какие команды создали среду.

Удалим только ресурсы этого эксперимента:

```bash
docker rm lesson4-edit
docker image rm lesson4-snapshot:1
```

## Кэш сборки

Повторите сборку `lesson4-python:1`. Docker может повторно использовать результаты неизменившихся шагов — в выводе появится `CACHED`.

Теперь измените сообщение в `main.py` и соберите образ ещё раз. Установка пакетов должна остаться в кэше, поскольку `requirements.txt` скопирован до исходного кода. Если сначала выполнить `COPY . .`, любое изменение кода может привести к повторной установке библиотек.

Для сборки без использования кэша шагов:

```bash
docker build --no-cache -t lesson4-python:1 .
```

Обновление базового образа запрашивается отдельно флагом `--pull`. Даже после пересборки старый контейнер продолжает использовать прежний образ; создайте новый контейнер, чтобы увидеть обновление.

Дополнительно создайте `.dockerignore`:

```text
.git
.venv
__pycache__
*.pyc
.env
```

Он исключает ненужные файлы из контекста сборки — каталога, указанного последним аргументом `docker build`.

## Очистка: `docker builder prune` и `docker system prune`

Сначала посмотрите занятое место:

```bash
docker system df
```

`docker builder prune` очищает неиспользуемый кэш сборщика. `docker system prune` действует шире: удаляет остановленные контейнеры, неиспользуемые сети, dangling-образы и неиспользуемый кэш. Эти команды работают на уровне выбранного Docker Engine, а не текущей папки.

Поэтому в практике курса общую очистку **не выполняем**: она может затронуть другие проекты, включая остановленные контейнеры базы. Не добавляйте `--volumes` или `-a`, не разобравшись с областью удаления. Достаточно адресных `docker rm` и `docker image rm` с именами учебных ресурсов.

## Практика

1. Создайте три файла и соберите `lesson4-python:1`.
2. Запустите контейнер; проверьте вывод версии `requests`.
3. Повторите сборку без изменений, затем измените `main.py`. Сравните шаги с `CACHED`.
4. Выполните эксперимент с `commit` и прочитайте `/tmp/note.txt` из нового образа.
5. Объясните, почему установка библиотеки на хосте не заменяет `RUN pip install`.

## Кратко

- Зависимости приложения устанавливают при сборке образа.
- Порядок `COPY` и `RUN` влияет на повторное использование кэша.
- `commit` сохраняет изменения файлов контейнера, кроме подключённых томов.
- Общая очистка Docker может затронуть другие проекты.
